# Agent instructions

## Scope and working principles

- These instructions apply throughout the repository. Also read any `AGENTS.md` in the directories you modify; more-specific instructions take precedence within their scope.
- Read the relevant code, documentation, configuration, and tests before editing. Follow established patterns rather than introducing a parallel architecture.
- Make focused, complete changes. Do not perform unrelated refactors, replace working dependencies, or overwrite user changes.
- Fix root causes, not symptoms. Add regression coverage for bug fixes.
- Do not commit, create branches, or perform destructive operations unless explicitly requested.
- Keep documentation, examples, configuration, generated artifacts, and affected call sites consistent with behavior changes.
- Ask for clarification when a consequential product or architectural decision cannot be resolved from the repository. Do not invent requirements or claim unverified behavior.

## Repository and tooling

- `frontend/`: Next.js App Router, React, TypeScript, Tailwind CSS, and shadcn/ui. Use Bun and the existing `bun.lock`; do not introduce npm, Yarn, or pnpm lockfiles.
- `backend/`: Python package under `src/backend/`, using uv, Pydantic, FastAPI dependencies, and NetworkX. Use `pyproject.toml` and `uv.lock`; do not introduce a separate pip-based workflow.
- `backend/tests/`: existing Python `unittest` coverage.
- `shared/graphql/`: shared GraphQL schema and scalar configuration.
- `docs/api_references/`: provider contracts, including the Ignav OpenAPI reference.
- `justfile`: shared setup, code-generation, and component-preview commands.
- `mise.toml`: pinned development tools. Prefer these versions over arbitrary system installations.
- Read `frontend/AGENTS.md` before frontend work. It requires checking the installed Next.js documentation under `frontend/node_modules/next/dist/docs/` before writing Next.js code; do not assume older framework APIs still apply.

## Frontend: shadcn/ui first

- Use shadcn/ui for every applicable UI primitive: buttons, inputs, selects, checkboxes, dialogs, sheets, popovers, menus, tabs, tooltips, tables, calendars, and similar controls.
- Before building a component, inspect `frontend/components/ui/` and existing application components. Reuse what exists; add the appropriate shadcn/ui component when a suitable primitive is missing.
- Follow `frontend/components.json`, including the current Base UI-backed `base-nova` style, aliases, CSS variables, and Lucide icons. Do not assume Radix-specific APIs or introduce a competing component library.
- Build custom application elements by composing or extending shadcn/ui primitives. Keep reusable primitives in `components/ui/` and domain-specific compositions in the surrounding components directory.
- Only implement an independent custom primitive when shadcn/ui cannot reasonably support the interaction. Explain the limitation and preserve equivalent accessibility and testing standards. Ordinary semantic HTML and layout elements do not need artificial shadcn wrappers.
- Prefer composition and explicit variants over copied components, ad hoc overrides, or increasingly complicated conditional styling. Use existing class-merging utilities and variant patterns.
- Use shared theme tokens and Tailwind conventions. Avoid hardcoded colors, one-off spacing systems, and duplicated global styles. Respect existing light/dark theme behavior.
- Use the existing Lucide icon library. Give icon-only controls accessible names; hide decorative icons from assistive technology.
- Treat keyboard navigation, focus visibility, focus trapping/restoration, labels, descriptions, validation feedback, and screen-reader semantics as requirements, not optional polish.
- Design responsive layouts for narrow and wide screens. Account for long content, touch targets, overflow, reduced motion, and loading, empty, error, disabled, and success states where relevant.
- Preserve semantic HTML and native behavior. Do not replace buttons or links with clickable generic elements.
- Prefer Server Components; introduce client boundaries only for state, event handlers, browser APIs, or client-only dependencies. Keep secrets and server-only logic out of client bundles.
- Keep TypeScript strict and model states explicitly. Avoid `any`, unsafe assertions, and suppression comments unless necessary and explained.
- Use the existing `components/**/*.preview.tsx` convention for new or materially changed reusable components when useful. Preview registries are generated by `frontend/scripts/gen-previews.ts`; do not edit the generated registry manually. Previews support review but do not replace automated tests.

## Backend and domain correctness

- Keep domain logic separate from transport, provider adapters, and CLI handling. Validate untrusted inputs at boundaries and use typed models for contracts.
- Preserve meaningful distinctions between missing, null, zero, false, and empty values. Validate ranges and cross-field constraints explicitly.
- Handle dates, currencies, and identifiers deliberately. Use timezone-aware datetimes, enforce schedule feasibility where required, and preserve decimal precision across serialization boundaries.
- Preserve parallel flight edges in multigraphs. Static route connectivity does not establish time-feasible itineraries, and bundled itinerary prices must not be summed as independent segment fares.
- Keep synthetic data clearly labeled. Do not present mock schedules, prices, booking links, or generated locations as real availability.
- Keep fixtures deterministic through explicit seeds and fixed dates. Avoid global random-state dependencies and accidental dependence on the current clock.
- Return actionable errors without leaking secrets or internal details. Keep CLI machine-readable output on stdout and diagnostics on stderr.

## Shared contracts and generated code

- `shared/graphql/schema_v1.graphql` is the source of truth for the shared GraphQL contract. Ignav models derive from `docs/api_references/ignav/openapi.json`.
- Do not hand-edit `backend/src/backend/infrastructure/graphql/models.py`, `backend/src/backend/infrastructure/ignav/models.py`, files under `frontend/generated/`, or other explicitly generated outputs. Change their inputs or generator configuration and regenerate them.
- Use canonical backend modules under `domain/`, `application/`, `infrastructure/`, and `presentation/`. Do not reintroduce retired flat modules or the `mock/`, `graphutils/`, `models/`, and `generated/` compatibility packages; see `backend/README.md` for migration paths.
- For schema changes, update affected consumers, validation, serialization, and contract tests together. Documentation-only schema constraints still need application-level enforcement.
- Preserve configured scalar mappings, decimal precision, and serialized field aliases. Test round trips across the relevant boundaries.
- Check generated changes for unintended drift and confirm generation is deterministic when modifying the generation workflow.

## Comprehensive testing requirements

### Required coverage

- Every behavior change must have automated coverage at the appropriate level. For bug fixes, add a test that reproduces the failure and would fail without the fix.
- Test observable behavior and public contracts rather than implementation details. Prefer meaningful assertions over broad snapshots or tests that merely check rendering.
- Cover the happy path, realistic edge cases, invalid input, boundary values, empty results, and relevant failure/recovery paths. Include permissions and security boundaries when applicable.
- Use unit tests for isolated domain logic and utilities; component tests for interactive UI; integration tests for contract and subsystem boundaries; and end-to-end tests for critical user journeys.
- For frontend changes, cover user interactions, validation, loading/error/empty states, and keyboard accessibility as applicable. Check responsive behavior and theme compatibility for visual changes.
- For forms and overlays, verify accessible names, focus behavior, submission, dismissal, and error feedback. Automated accessibility checks supplement, not replace, keyboard and visual review.
- For API/provider work, cover request validation, response serialization, aliases, nullable fields, upstream failures, and timeouts/retries when implemented. Mock external services at boundaries; do not mock away the behavior being tested.
- For flight/date/graph logic, cover timezone and DST transitions, ordering, connection constraints, price semantics, duplicate/parallel edges, reproducibility, and serialization as relevant.
- For CLI changes, check exit status, valid machine-readable stdout, stderr diagnostics, malformed input, and representative end-to-end invocation.
- Add performance or scale regression checks when changing algorithms or potentially expensive rendering/data operations. Prefer stable bounds or benchmarks over flaky wall-clock assertions.

### Test quality and tooling

- Keep tests deterministic and independent: fix clocks and seeds, isolate mutable state, and avoid live network calls, credentials, arbitrary sleeps, and test-order dependence.
- Use small, representative fixtures; clean up files, processes, and other resources. Make failures descriptive and easy to reproduce.
- Follow the existing backend `unittest` conventions. Reuse existing frontend test tooling if present.
- The current frontend package has no test script or configured component/E2E runner. When adding frontend behavior that needs coverage, establish a minimal compatible setup rather than omitting tests or claiming lint/build are sufficient. Prefer React Testing Library with a compatible runner for component tests and Playwright for browser journeys; avoid redundant test frameworks.
- Keep any new test dependencies scoped appropriately and update the lockfile. Do not install a large testing stack for documentation-only or otherwise unrelated changes.
- Do not weaken assertions, skip tests, lower quality gates, or regenerate snapshots blindly to make a change pass. Investigate failures and distinguish regressions from pre-existing issues.
- Aim for thorough coverage of changed behavior and critical paths, not an arbitrary coverage percentage. Do not describe unexecuted tests or manual checks as passed.

### Validation commands

Run from the repository root unless noted. If tools are not on `PATH`, use `mise exec --` before the command.

```sh
# Install pinned tool versions and locked dependencies when needed.
mise install
mise exec -- just setup

# Backend suite; use unittest module/pattern selection for focused runs first.
uv run --project backend --locked python -m unittest discover -s backend/tests -v

# Frontend static checks and production build.
bun run --cwd frontend lint
bun run --cwd frontend tsc --noEmit
bun run --cwd frontend build

# Regenerate shared GraphQL types/models when their inputs change.
just codegen

# Regenerate Ignav models when their inputs change.
just codegen-ignav
```

- Run the narrowest relevant tests first, then broader affected suites and checks. For frontend behavior, also run the component/browser tests added or configured for that work; the commands above do not substitute for them.
- For UI work, use the existing `just preview` workflow when helpful and inspect the affected states. Do not claim a visual or browser check unless you actually performed it.
- For documentation-only changes, verify paths, commands, and factual claims; full application suites are not required unless the change affects executable examples or workflows.
- Before finishing, review the diff for accidental changes, debug code, secrets, generated-file mistakes, and missing tests or documentation.
- Report what changed, the exact checks run and their outcomes, and any unverified behavior or remaining failures. If a check cannot run, state why and what remains to verify.

## Security and dependency discipline

- Never commit secrets, credentials, private user data, or local environment files. Use environment configuration and document required variable names without real values.
- Treat external input and provider responses as untrusted. Avoid unsafe HTML, unchecked redirects, and unnecessary exposure of internal errors or data.
- Prefer existing dependencies. Add new ones only for a clear requirement, check compatibility with pinned versions, and keep manifests and lockfiles synchronized.
- Do not silently make tests depend on billable services or live provider APIs. Keep ordinary validation offline; document any intentional external integration checks and their prerequisites.
